## 背景

P5 面向小孩与特殊人群，希望内容可以被**读出来**。用户最初的需求是「朗读内容和语音输入」。这两件事
名字相近，实现的离线可行性却完全不同：

| 方向 | 技术 | 是否联网 |
| --- | --- | --- |
| 朗读（TTS） | 浏览器 / 系统内置 `speechSynthesis` | **不联网** |
| 语音输入（STT） | 浏览器或云端的语音识别 | 浏览器内置识别在多数实现里**会把录音送到云端** |

## 决策

**做朗读，不做语音输入。**

- 朗读用 `window.speechSynthesis` 在**本机**合成，文本不出这台机器，与「儿童档不出站」的一档 `none`
  策略一致（第 7.7 节）。语速等偏好只写 `localStorage`，不进服务端。
- **不引入任何语音输入入口**：录音上传识别会把音频发到云端，直接违背儿童档的隐私承诺。
  `FormRenderer` 里 YAML 声明的 `widget.child: voice_first` **按类型回退成普通文本输入**，
  不是漏实现，是刻意不做（见 [formUtils.ts](file:///d:/AI%E8%BD%AF%E4%BB%B6/LifeOS/apps/web/src/lib/formUtils.ts) 的注释）。

## 影响

- `apps/web/src/lib/readAloud.ts`：纯函数 `canSpeak()` / `clampRate()` / `splitSentences()`。
- `apps/web/src/components/ReadAloud.tsx`：播放 / 暂停 / 继续 / 停止 + 语速 + 逐句高亮；
  卸载或切换文本时立刻 `cancel()`，避免界面切走后声音还在后台念。
- 能力探测：本机没有朗读能力时**不渲染**按钮（而不是给一个点不动的灰按钮）。
- 入口挂在条目列表、报告阅读器、儿童档表单的说明文案上（方案 5b.3 / 5b.6）。
- 儿童档「朗读是否真的离线」的验证记在 [child-data-checklist.md](file:///d:/AI%E8%BD%AF%E4%BB%B6/LifeOS/docs/compliance/child-data-checklist.md)：
  断网后仍能朗读，即证明走的是本机合成。

## 备选方案（不采纳）

若将来确实需要语音输入，必须**先**新开 ADR：要么只在成人档开放并明确告知录音会出站，
要么接入纯本机识别模型（体积与算力代价另议）。本期不做。
